## 1. 项目背景

### 1.1 业务背景

网络设备的登录认证、命令授权和操作审计是一条连续的运维链路。网络设备、边缘节点和人工审批如果各自维护账号与权限，账号状态、角色范围、可执行命令和目标设备范围容易出现不一致。人员变更、临时提权、值班切换和权限回收也容易依赖人工处理，发生故障或安全事件后，难以按用户、交换机、目标服务器和命令完整追溯。

当 TACACS+ Client 通过负载均衡或跨网络链路提供服务时，还需要处理真实交换机地址透传、连接复用、链路拥塞下的控制面流量优先级、节点健康检查和多节点配置收敛等问题。仅在单台设备上配置 TACACS+ 参数，无法解决这些集中治理和持续运营问题。

### 1.2 项目要解决的实际问题

| 实际问题 | 具体表现 | 对运维和安全的影响 |
| --- | --- | --- |
| 账号和状态分散 | 用户、密码、启停状态分散在设备或多个边缘节点，停用和改密需要多处操作 | 离职、转岗或账号泄露后的回收不及时，容易出现脏账号 |
| 权限粒度不足 | 只控制“能否登录”，难以同时约束角色、命令和目标服务器 | 用户可能获得超出职责范围的命令或设备访问权限 |
| 临时权限缺少闭环 | 临时授权没有统一申请、审批、到期和回收链路 | 临时权限可能长期保留，审批过程和责任人难追溯 |
| 多节点配置不一致 | 多个 TACACS+ Client 节点的用户和角色数据刷新方式不统一 | 同一账号在不同节点上得到不同结果，故障排查困难 |
| 审计数据分散 | 认证、授权、记账和管理操作日志分布在不同节点 | 难以回答“谁在什么时间、从哪台设备、对哪个目标执行了什么命令” |
| 高峰或链路异常影响认证 | 短连接、负载均衡、NAT、拥塞和半开连接会影响网管面请求 | 设备登录和命令执行可能受到网络抖动影响，且真实来源地址丢失 |
| 管理入口容易被绕过 | 管理 API、浏览器会话和跨机调用需要不同的身份校验 | 后端暴露或请求头被伪造时可能造成越权操作 |

### 1.3 项目定位与建设思路

本项目采用“中心管理、边缘执行”的架构：

- **SwM** 是统一 Web 入口，负责登录会话、HTTPS、CSRF、防重放、ACL 和反向代理。
- **Server** 负责用户、角色、命令模板、服务器模板、审批、权限生命周期和持久化，并通过 MySQL 管理数据。
- **Client** 部署在网络设备可达的边缘节点，承接 TACACS+ TCP 49 流量，执行认证、授权和计费，并以只读数据库、本地缓存和原子刷新保障认证热路径。

通过这一分层，账号和权限在中心统一维护，TACACS+ 请求在边缘就近处理，管理面与认证数据面相互隔离。

## 2. 收益

### 2.1 直接收益

| 收益方向 | 项目能力 | 能解决的问题 | 建议关注的结果指标 |
| --- | --- | --- | --- |
| 统一账号治理 | 用户 CRUD、密码 bcrypt 存储、用户状态、角色模板、值班用户和白名单 | 减少设备侧重复配置，统一停用、改密和恢复流程 | 账号变更覆盖率、停用/改密生效时延、异常账号数 |
| 最小权限控制 | 角色绑定命令正则和服务器 IP/CIDR，Client 对命令和目标服务器同时校验 | 把“能登录”细化为“能执行哪些命令、访问哪些目标” | 越权请求拒绝率、权限规则覆盖率、误授权事件数 |
| 临时授权闭环 | 审批工单、有效期、审批状态、超时关闭、到期回收和飞书通知 | 临时提权有申请人、审批人、有效期和回收记录 | 审批处理时长、到期回收成功率、超期权限数 |
| 权限变更快速收敛 | `tacacs_meta` 版本号、数据库触发器或应用 bump、Client 周期刷新、5 分钟兜底和管理员强刷 | 避免多 Client 节点长期使用旧权限 | 变更到各节点的收敛时间、缓存重建成功率、节点间结果一致性 |
| 审计和追责 | 认证、授权、记账 JSON 文件日志，Server/SwM 审计日志，可选 ClickHouse 或外部日志跳转 | 支持按用户、设备、目标、命令和时间回溯操作 | 审计事件完整率、查询成功率、日志保留周期、追溯耗时 |
| 认证链路可靠性 | Single-Connect/Mux、TCP NoDelay/KeepAlive、DSCP、可选 PROXY protocol、健康检查和无状态 Client | 降低连接建立和链路抖动对网管面的影响，支持 LB 扩容并保留真实交换机地址 | 认证成功率、P95/P99 延迟、连接复用率、节点故障切换结果 |
| 管理面安全 | SwM 单入口、IP 白名单、HMAC + nonce + 时间窗、CSRF、安全响应头、登录限流和失败锁定 | 降低后端直达、请求伪造、暴力登录和管理员越权风险 | 越权用例拦截率、登录攻击拦截率、密钥/证书轮换完成率 |
| 运维效率 | 三个服务统一配置、优雅停止、panic 飞书告警、Makefile、Docker 构建和部署脚本 | 降低部署、升级和故障发现成本 | 部署耗时、回滚耗时、故障发现时延、人工操作步骤数 |

### 2.2 预期业务价值

1. 将网络设备 AAA 从“各设备和各节点分别维护”收敛为统一的用户、角色、命令和目标设备模型。
2. 将临时权限从口头或人工操作转为可审批、可追踪、可自动回收的流程。
3. 将认证授权结果与管理操作关联起来，为安全审计、故障排查和责任界定提供统一证据链。
4. 在不把中心管理服务直接放到认证热路径上的前提下，支持边缘 Client 横向扩展和权限缓存。
5. 为后续接入日志平台、排班系统、工单系统、统一身份源和多副本部署保留接口和演进空间。

### 2.3 收益边界

以下内容属于当前代码中的设计能力或可选集成，不能直接视为已经达成的生产指标：

- README 中的“2 秒级同步”“毫秒级响应”等描述需要通过真实 MySQL、网络设备、负载均衡和多节点压测确认。
- ClickHouse 直查和 LogHub 上报需要按部署配置接入外部服务；当前仓库不等同于已经提供完整的日志平台。
- 当前主要适配 MySQL，数据库初始化仍以 SQL 文件执行为主，完整迁移、备份恢复和灾备流程需要后续建设。
- 当前自动化验证以单元测试、安全边界和 SQL 构造测试为主，真实设备、Apollo、ClickHouse、LB 和多副本故障场景需要集成验证。

- TACACS+ Authentication、Authorization、Accounting 三类处理能力。

### 3.3 每个阶段的通用验收清单

- 业务流程：正常、拒绝、超时、重复提交、到期回收和恢复场景均有记录。
- 安全边界：普通用户、管理员、未签名请求、重放请求、越权请求和跨网访问均按预期处理。
- 数据一致性：中心配置变更后，所有 Client 的权限结果在目标时限内一致。
- 可观测性：成功、失败、延迟、缓存刷新、数据库异常和外部日志异常均能定位。
- 运维交付：配置样例、部署步骤、升级步骤、回滚步骤、备份恢复步骤和责任人齐全。
- 质量门禁：代码测试、竞态测试、静态检查、构建和变更审查通过后再进入下一阶段。
